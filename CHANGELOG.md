# Changelog

## Unreleased

### Added

- Document onboarding a company: the README, `jobs/README.md` and `packs/README.md` describe `jobs.profile`, `jobs.ingest_docs`, `jobs.draft_pack`, the Review, Documents and Datasets sections and how reviewed YAML is committed through a pull request.
- Add `packs/ecommerce_twin_regen`, the hand-written pack with its 36 dataset, column, metric and glossary descriptions drafted from the mart profile and reviewed in the console; it scores the same 39/45 execution match as the hand-written pack case for case, recorded in `docs/eval/ecommerce_twin_regen-report.md`.
- Onboard a pack before its first compile: `/me`, `/pack`, Review and Documents read the active pack's name, display name and roles from `compiled.json` and, while the pack was never compiled, from its `business_profile.yaml` and `policies.yaml`, so a reviewer can sign in and approve drafts that the compiler would still refuse; questions and `/datasets` keep needing the compiled pack.
- Wire the console's Datasets, Review and Documents sections to the api: their Sample data badges are gone, the web server forwards `/api/datasets`, `/api/review/items/...` and `/api/documents/...` with the session's token (uploads as the original multipart body), a new document may be read by every pack role until the reviewer narrows it, upload and draft errors show the api's reason, uploads wait while the pack compiles, and the provisional `DatasetView`, `ReviewItem` and `DocumentRow` types are replaced by types generated from the api's contracts.
- Review pack items from the api: `GET /review/items` lists every item of the eight pack files by file and status with its evidence (a deleted cited document is flagged), `PATCH` edits its text or formula and returns it to `draft`, `POST .../approve` approves it after a clean test-run of its metric, example or eval SQL, `POST .../test-run` runs that SQL as `pack_review` with `readonly=2` and the `QUERY_MAX_*` limits, and `DELETE` removes it; changes are written to the pack's working tree, checked against the schema and refused while the pack compiles. `GET /datasets` lists the compiled pack's datasets with their columns and the roles granted each; all of these answer only a `pack_reviewer`.
- Draft pack items for review: `jobs.draft_pack --pack <name> --allow-billable` (without the flag it prints the prompt size and exits 2) and `POST /documents/{id}/draft` send one `sql-gen` call per file for `datasets.yaml`, `glossary.yaml`, `metrics.yaml` and `examples.yaml` from the profile and document chunks; drafts keep only evidence found in the input, never replace an approved item, fill an existing draft's text without changing its ids or SQL, and every drafted metric and example query is test-run so a failure stays a draft with the error as evidence.
- Edit pack YAML item by item without losing what people wrote: drafts are appended or refresh existing drafts and never replace an approved item, an edited item returns to `draft`, comments, anchors, quoting and order survive, a file nothing changed is never rewritten, and every save is checked against the file's JSON Schema and replaces the file atomically.
- Rebuild `kb_docs` from the document registry on every compile: `compile_pack` holds `build/packs/<pack>/compiling` so the api refuses document changes, waits up to two minutes for uploads still processing, copies the live chunks of indexed documents with their vectors when `compiled.json` records the same `embedding_alias`, and otherwise re-parses, screens and embeds the stored files, reporting a document whose file is missing.
- Manage company documents from the api: `POST /documents` (multipart `file` and `allowed_roles`), `GET /documents`, `PATCH /documents/{id}` (roles) and `DELETE /documents/{id}` answer only a `pack_reviewer`, return 409 for a duplicate or while the pack compiles, 413 above `DOCUMENT_MAX_BYTES` and 415 or 422 for a file that cannot be read; `jobs.ingest_docs --pack <name> --folder <dir>` loads a folder listed in its `manifest.yaml` through the same code, and a pack that was never compiled gets its `kb_docs` alias on the first upload.
- Index company documents into the pack's live `kb_docs` alias: an upload is checked (pack not compiling, size cap, roles of the pack, type from the content, SHA-256 new for the pack), stored, parsed, chunked, screened chunk by chunk, embedded and written as `{id, type, document_id, source, heading_path, text, allowed_roles, pack}` chunks; a failure or a document whose every chunk screening blocked is marked `failed` with no chunk and no stored file left, delete removes the chunks and the file, and a document's roles can be changed on its chunks in place.
- Read company documents for `kb_docs`: the type comes from the file content (PDF with a text layer, DOCX, XLSX values without evaluating formulas, Markdown and UTF-8 text), macro-enabled Office files, other archives, binaries, empty files, scanned PDFs and non-UTF-8 text are refused, parsing stops at 500 PDF pages or 50 000 sheet rows, and chunks of at most 2 000 characters stay under one heading, page or sheet, with each sheet block repeating its header row.
- Profile a pack's marts without an LLM: `jobs.profile --pack <name> [--tables a,b]` writes `build/packs/<pack>/profile.json` with each table's row count, each column's type and distinct count, date ranges, top values of low-cardinality strings, sample rows and join-key candidates with their value overlap; the drafter cites these facts as evidence.
- Register company documents per pack: `data_meta.documents` (fresh volumes through `infra/clickhouse/initdb/030-documents.sql`, existing ones through `jobs.apply_log_schema`) records each document's file, type, size, SHA-256, uploader, `allowed_roles`, status and chunk counts, the new `pack_review` ClickHouse user is the only api user that writes it and reads `marts` for reviewer test-runs, the `documents` volume keeps the originals, and `api` and `jobs` mount `./packs` so reviewed YAML lands in the working tree.
- Declare a pack's data source by kind and mode: source manifests under `jobs/sources/` take `kind` (`huggingface`, `postgres`, `mysql`, `mongodb` or `files`), `mode` (`copy`, the default, or `live`), the `connection_env` prefix of the source's `<PREFIX>_HOST`, `_PORT`, `_DATABASE`, `_USER` and `_PASSWORD` variables, and per-table source names, MongoDB column types or S3 object keys with their format; `jobs/sources/source.schema.json` validates them, `expected_rows` becomes optional outside Hugging Face sources, and manifests may share a dbt tag when they declare the same tables. The `ecommerce_twin` manifest is unchanged and reads as `kind: huggingface`.
- Keep source credentials in ClickHouse only: `infra/clickhouse/config.d/sources.xml` defines one named collection per source from the clickhouse service's environment, and the new `source_loader` user (`CLICKHOUSE_SOURCES_PASSWORD`) is the only one allowed to use them, so engine definitions, sync queries and `system.tables` name a collection and never a password, and the `jobs` service never receives a source credential.
- Copy a source into ClickHouse with `jobs.sync_sources --source <name>`: each table is read through `postgresql()`, `mysql()`, `mongodb()` or `s3()` into `raw.<source>__<table>__loading`, counted against the manifest and exchanged into `raw.<source>__<table>` only when every table matches, so a failed sync keeps the previous copy.
- Read a source live: in `live` mode `jobs.sync_sources` creates `src_<source>` with a `PostgreSQL` or `MySQL` database engine, or a `MongoDB` or `S3` table engine per table, and dbt builds the marts as views with `SQL SECURITY DEFINER` over it, so agent roles are granted marts only and never `src_*` or `raw`. `jobs.refresh_data` now syncs any source kind, passes the relations of its tables to dbt and takes `--mode` to override the manifest.
- Add the `sources` Compose profile with lab fixtures of a company's systems: PostgreSQL, MySQL, MongoDB and an S3-compatible SeaweedFS store, each seeded with one small synthetic widget dataset (40 widgets, 3,000 sales, 300 refunds, written by `infra/sources/fixtures/generate.py`) and a read-only user.

- Route SQL generation by query complexity: a deterministic rule scores a QuerySpec as simple (one metric, at most one dimension, one period, no comparison, no top N) or standard; `generate_sql` uses the new `sql-small` tier for a simple spec and `sql-gen` otherwise, a retry after a `sql-small` attempt moves to `sql-gen` and the third retry keeps `sql-gen-hard`. Each attempt records its tier, the run's `generate_sql` event carries the score, and every gateway request sends its tier as metadata.
- Offer models from several providers behind the LiteLLM catalog: `infra/litellm/catalog/` has one file per provider (OpenAI `openai-small`, `openai-medium`, `openai-large`, `openai-embed`; Anthropic `anthropic-small`, `anthropic-medium`; Gemini `gemini-small`, `gemini-medium`; Ollama `local-small`), and the proxy's new entrypoint `build_config.py` loads a provider's aliases only when `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY` or `OLLAMA_URL` is set, so the gateway starts and stays healthy with any subset of keys. The optional `local-models` Compose profile runs Ollama for the local alias.
- Map each model tier to a catalog alias at run time: engine code calls the tiers `fast`, `sql-small`, `sql-gen`, `sql-gen-hard` and `embed`, whose defaults come from `MODEL_TIER_<TIER>` in `.env`; the api reads changed mappings from the new `data_meta.model_tiers` table (`ReplacingMergeTree`, written and read by the new `model_tiers_admin` ClickHouse user with `CLICKHOUSE_MODEL_TIERS_PASSWORD`) at most 30 seconds later, needs no LiteLLM restart, and keeps the defaults when the table cannot be read. `embed` always keeps its default.
- Record the model tier of every gateway call in the new `agent_logs.llm_calls.tier` column, filled by the LiteLLM callback from the request metadata, beside the catalog alias it resolved to; `jobs.apply_log_schema` adds it, the new `eval_reports` columns, `agent_logs.admin_actions` and `data_meta.model_tiers` to an existing volume.
- Prove an alias for a tier with the pack eval: `jobs.eval --tier <tier>=<alias>` runs a chat tier on another catalog alias, the report lists the run's tier mapping and the share of SQL first generated by `sql-small` with its escalation rate, and `agent_logs.eval_reports` stores, as eligibility evidence, the mapping of the tiers the run actually called (`tiers`; empty for a run with `--only`, a threshold below the default 80% or a reference error) and whether the run regressed against its baseline (`regressed`, NULL without one). An alias is eligible for a tier when the latest report that called the tier with it met the threshold without regression.
- Manage model tiers from the api: `GET /admin/models` lists every tier with its alias, provider, default, eligibility and the report behind it, and for each chat tier the aliases the gateway loaded with their eligibility; `PUT /admin/models/{tier}` (`admin` only) accepts only an eligible loaded alias, refuses `embed`, writes the mapping, records the change in the new `agent_logs.admin_actions` table (`ts, actor, action, target, old_value, new_value`) and writes the previous alias back when the audit row cannot be written, unless the tier changed again meanwhile; changes run one at a time and each mapping row is newer than the last. The tier lookup reaches the model store on every refresh, so a store that was down at startup is used once it is back, and `jobs.ask` reads the same mapping.
- Add the console's Models section for an `admin`: each tier shows its model, provider, default and eligibility, an eligible model is chosen after a confirmation, every choice is disabled while a change saves, and an ineligible one is disabled with the reason beside it; `embed` is shown without a choice. The section reads the api through the web server's `/api/admin/models` routes and the generated `ModelTiers` contract types, with no Sample data badge.
- Score definition questions in the eval: the new `definition` category runs `metadata_qa` and passes when its answer, written without SQL, came from every hit labelled in the case's `expected_sources` (`<index>:<key>`); the `ecommerce_twin` set adds four English and four Vietnamese definition cases, and its string-filter cases label the column values they filter on.
- Measure search per collection: `jobs.retrieval_eval --pack <name>` searches every labelled eval question as its case's role and reports recall@5, recall@10 and nDCG@10 per collection and language, the queries that missed a source, and a before/after table against an earlier JSON report.
- Document input screening: the README explains fetching the classifier, the two screening modes and the measurement, and the infra README describes the gateway guardrail and how its rules copy is kept in step.
- Show a blocked question in the chat: a `blocked` event renders a notice in the answer's language with the api's message, never the question, and the step list starts with Checking the question for the `screen` node; the sample chat streams `status -> blocked -> done` for the `ecommerce_twin` sample scenario `instructions_override`, and the sample scenario schema accepts kind `blocked` with its `screened_message`.
- Fetch the screening classifier outside Git: `docker compose run --rm guard-model` runs `jobs.fetch_guard_model` in its own PyTorch image, downloads one pinned revision of the gated `meta-llama/Llama-Prompt-Guard-2-86M` with `HF_TOKEN` (passed to that service only and never printed), exports it to ONNX, checks the export with the api's classifier against PyTorch and known inputs and writes it with its version to the new `guard-models` volume, which `api` and `jobs` mount read-only; `.env.example` documents `SCREEN_MODE`, `SCREEN_FLAG_AT`, `SCREEN_BLOCK_AT` and `HF_TOKEN`.
- Measure screening before enforcing it: `jobs.screen_eval --pack <name>` screens a benign set (the pack's eval questions and sample questions plus an engine-level English and Vietnamese set) and about 100 hand-written English and Vietnamese attacks, direct and inside document text, with the local classifier and no LLM call, and prints the false-positive rate, recall, latency and misclassified items per language and whether the DECISIONS §9 enforcement gate holds.
- Screen document chunks and column values while a pack compiles: a `kb_docs` chunk the screener blocks, or any chunk while the classifier is unavailable, is not indexed and is listed in the compile report; a flagged or blocked low-cardinality column value is listed and still indexed; the compile's embedding requests carry `trusted_pack` screening metadata.
- Reject LLM gateway requests the api did not screen: the LiteLLM `pre_call` guardrail `infra/litellm/callbacks/screening_guard.py` answers HTTP 400 `screening_guard: ...` to a request without `allow`, `flag` or `trusted_pack` screening metadata and reruns the EN/VI rules (except the prompt-tag rule the api's own templates trip) on every message and embedding input; it reads a byte-identical copy of the api's rules, and a test fails when the two copies differ.
- Screen every question before any LLM call: the new first graph node `screen` writes one `agent_logs.input_screening` row per question (verdict, mode, score, rule hits, model version; 90-day TTL, created on a fresh volume and by `jobs.apply_log_schema` on an existing one). `SCREEN_MODE=log` (default) records the verdict and lets the run continue; `enforce` stops a `block`; an `unavailable` verdict stops the run in both modes. A stopped run streams `status* -> blocked -> done`, the new `BlockedEvent {message, lang, trace_id}` in the question's language that never repeats the question, and its question is not stored as a conversation turn: `/ask` now writes the question once `screen` lets it through.
- Send every LLM call as a `system` message with the prompt's rules and a `user` message with its untrusted content: new prompt versions `router.v3`, `extract.v4`, `generate_sql.v2`, `metadata_qa.v2`, `out_of_scope.v2`, `chart_recommender.v2` and `summarize.v2` split at a `<!-- user -->` line. Every gateway request of a run carries `screening` metadata (`allow`, or `flag` for a flagged question and for a block that log mode lets through); calls on reviewed pack content outside a run (compiles, `jobs.smoke_llm`) carry `trusted_pack`. A request the gateway's screening guardrail rejects ends the run with the `blocked` reply.
- Report whether questions can be screened on `/health`: it stays a liveness check and adds `screening: ready | unavailable` with the classifier version, so Compose and CI never depend on the gated model; `jobs.ask` and `jobs.eval` screen their questions like the api.
- Screen untrusted text locally before it reaches an LLM (DECISIONS §9, Layer 0): `app.screening` matches high-precision English and Vietnamese rules on folded text (attempts to ignore or replace earlier instructions, reveal the system prompt, role-play as the system or developer, and fake prompt boundaries) and scores the text with the Prompt Guard classifier exported to ONNX, over overlapping 512-token windows (at most 8), into `allow`, `flag` (`SCREEN_FLAG_AT`, default 0.5) or `block` (a rule hit or `SCREEN_BLOCK_AT`, default 0.9); without the classifier in `GUARD_MODEL_DIR` every verdict is `unavailable`. The api adds `onnxruntime`, `tokenizers` and `numpy`.
- Record answer feedback: `POST /feedback` takes a `like` or `dislike` with an optional note of up to 1,000 characters for one of the signed-in user's stored answers, found by its trace id, and writes it to `agent_logs.feedback`; another user's or an unknown trace id is 404 and nothing is written. The `agent_conversations` ClickHouse user may insert into `agent_logs.feedback`, and the web app's TypeScript `FeedbackInput` is generated from the new Pydantic model.
- Send the chat's like and dislike to the api instead of sample data: the web server's `/api/feedback` route forwards them with the session's access token, and the feedback feature no longer shows the Sample data badge.
- Choose each answer's chart by the DECISIONS §8 rules instead of always offering the table: a new `chart_recommender` node after `shape_result` picks a KPI for one row and one number, a line for time and a number (at most 6 series), a bar for a category and a number (at most 20 groups, horizontal when a label is longer than 12 characters), a grouped bar for a comparison group or a measure per compared period, a scatter for two numbers and the table otherwise; `allowed_types` lists only the types the same `x`, `y` and `series` can be drawn as, so a time series never allows a pie. When one category and one measure of at most 6 non-negative groups suit both a bar and a pie, the `fast` alias (prompt `chart_recommender.v1`) reads the question, never the rows, to choose, keeping the bar when its reply cannot be used; a chart edit draws the type asked for when the rules allow it and calls no LLM.
- Add the optional bar `orientation` (`vertical` or `horizontal`) to the ChartSpec contract in DECISIONS §7, its Pydantic model and the generated TypeScript types, and draw charts in the web app from the generated type instead of the provisional `OrientedChartSpec`.
- Keep the chat sidebar's conversations in the api instead of browser storage: the web server's `/api/conversations` and `/api/conversation-groups` routes forward list, search, read, rename, pin, group and delete to the api with the session's token, a new chat starts without an id and takes the one the api names in `X-Conversation-Id`, edit and retry send `edit_of_turn` and `retry_of_turn`, the conversations feature drops its Sample data badge, and the browser's provisional conversation types give way to the generated contract types.
- Manage conversations from the api: `GET /conversations` lists the signed-in user's conversations by latest activity with `limit` and `offset`, `GET /conversations/search?q=` matches titles and the user's own questions ignoring case and diacritics, `GET /conversations/{id}` returns the current thread with each answer's stream events, `PATCH`/`DELETE /conversations/{id}` rename, pin, group or hide one, and `/conversation-groups` creates, renames, lists and deletes personal groups (deleting a group moves its conversations back to no group); another user's or a deleted conversation or group is 404, changes write new `ReplacingMergeTree` rows, and the generated web contract types include these models.
- Edit or retry an earlier question: `/ask` takes `edit_of_turn` or `retry_of_turn` with the conversation's id, asks the new or stored question under a new revision of that turn with only the turns before it as context, and the turns after it leave the conversation; a turn outside the thread is 404.
- Keep each answer's stream events in `agent_logs.chat_messages.events` (without status events and without the result, whose rows stay in `result`), add the `agent_logs.conversation_groups` table, and let `agent_conversations` read and write it; `jobs.apply_log_schema` adds both to an existing volume.
- Score chart edits in the eval: the `chart_edit` category asks its `previous_question` first and passes when the previous result is redrawn without SQL; the `ecommerce_twin` set adds three chart-edit cases (line, bar and pie), and DECISIONS §6 lists the `metadata_qa` (`status* -> summary -> done`) and `chart_edit` (`status* -> result -> chart_spec -> done`) event sequences.
- Redraw the previous answer without SQL: the router (prompt `router.v2`) also reads the chart type a chart edit asks for, and the `chart_edit` branch reuses the QuerySpec and Result stored with the previous turn, asks `recommend_chart` (the chart recommender's entry point, which offers the table until the Phase 9 rules) for a ChartSpec and streams `status* -> result -> chart_spec -> done`, never calling `generate_sql` or `execute`; a chart edit with no previous result takes the data question flow.
- Answer definition questions without SQL: the `metadata_qa` branch searches the glossary, metrics, datasets and company documents (`kb_docs`) filtered by the asking role and asks the `fast` alias (prompt `metadata_qa.v1`) to explain the term from those hits only, in the question's language, never quoting figures from documents and treating retrieved text as data; it streams `status* -> summary -> done`.
- Score the router and the conversation branches in the eval: every active case scores the routed intent, ambiguous cases pass when the run asks a clarifying question, out-of-scope cases pass on a reply without SQL, and the new `follow_up` category asks its `previous_question` first in the same conversation; the `ecommerce_twin` set activates its three ambiguous and three out-of-scope cases and adds three follow-up cases ("What about last year?", a breakdown by category, the next year's monthly orders).
- Ask instead of refusing an ambiguous question: a question that names no measure, ranks by a word no business-profile convention defines, uses a term that fits several metrics or columns almost equally, or names no period ends at the gate with a `clarify` event whose options have stable ids (`metric:<id>` for up to four metrics the asking role may read, `column:<dataset>.<column>`, or `period:this_month` to `period:last_year`) and whose question is in English or Vietnamese; choosing an option sends its label as the next question, which `extract` reads with the earlier turn; the run is recorded as `clarified` and `jobs/ask.py` prints the question and options.
- Answer follow-up questions from the previous query: `extract` (prompt `extract.v3`) sees the conversation's recent questions and answers and the previous QuerySpec, restates a follow-up as the complete question it means, and gives a follow-up without its own period as a shift of the previous periods (`previous_periods`), which `resolve_time` applies and relabels deterministically, so "What about last year?" after a Q1 2024 versus Q1 2025 question asks for Q1 2023 versus Q1 2024 with the same measure, breakdown and ranking.
- Keep each `/ask` answer in its conversation: a question without `conversation_id` starts a conversation named in the response's `X-Conversation-Id` header, a follow-up with that id runs over the conversation's previous turns, an id that is not one of the user's own conversations is 404 and an unreachable conversation store is 503 before any LLM call; the question is stored when the turn opens and the answer before its last event is sent, and an out-of-scope question streams `status* -> summary -> done`.
- Reply briefly to out-of-scope questions without SQL: the `out_of_scope` node asks the `fast` alias (prompt `out_of_scope.v1`) for one or two sentences in the question's language saying what the assistant answers, falls back to a fixed English or Vietnamese reply when the gateway fails, records the run as succeeded with intent `out_of_scope`, and `jobs/ask.py` prints the reply and exits 0.
- Start every agent run with `load_context` and `router`: `load_context` loads the business profile, the last six turns of the conversation's current thread and the latest QuerySpec and result among them; `router` asks the `fast` alias (prompt `router.v1`) for the intent (`data_query`, `metadata_qa`, `chart_edit` or `out_of_scope`), its confidence and the question's language from the question, the recent questions and answers and the previous QuerySpec, never result rows, and assumes `data_query` when the reply is invalid or below 0.5 confidence; the run row records the routed intent, and `metadata_qa` and `chart_edit` still run the data question flow until their branches exist.
- Store conversations for follow-up questions: `ConversationStore` writes each question and answer to `agent_logs.chat_messages` with its turn, revision, QuerySpec and shaped Result, creates a conversation titled by its first question cut to 80 characters in the new `agent_logs.conversations` table, and reads back a conversation's current thread only for the user who owns it, through the new `agent_conversations` ClickHouse user (`CLICKHOUSE_CONVERSATIONS_PASSWORD`); `jobs.apply_log_schema` adds the new columns and table to an existing volume.
- Answer chat questions from the api instead of the sample scenarios: the web server's `/api/ask` route forwards the question with the browser's time zone and the session's access token to `POST /ask` and streams the server-sent events back, `lib/sse/parseStream.ts` reads them, Stop aborts the request so the api stops the run and its query, a refused request says why, and a stream that ends early shows the lost-connection notice. The chat's Sample data badge is gone; the suggested questions are still the pack's.
- Sign in to the web app through Keycloak instead of the demo identities: Continue with company account starts the OIDC authorization code flow with PKCE (S256) for the `finch-web` client, the callback checks the state against the browser's sign-in cookie and exchanges the code on the server, and the tokens stay in a server-side session behind an httpOnly cookie, refreshed before they expire; who is signed in and their roles come from the api's `/me`, a signed-out visitor is sent to the sign-in page, a failed sign-in says so, and Sign out ends the Keycloak session. The auth feature's Sample data badge and identity picker are gone, and features still on sample data act for the signed-in user.
- Generate the web app's TypeScript types for ChartSpec, the `/ask` request and every stream event from their Pydantic models, beside QuerySpec and Result; stream events are generated as the api sends them, so their `event` discriminator and `trace_id` are required. The web app's provisional ChartSpec, stream event and request types are deleted; its chat events are the generated ones plus the client's own network and stopped errors, and the chat now sends `timezone`.
- Stream answers from the api with `POST /ask`: an authenticated request runs the `data_query` graph as its pack role and returns server-sent events in the DECISIONS §6 order, `status` at the start and end of every node, the checked `sql` of each attempt, `result`, a table `chart_spec` until the chart recommender exists, `summary` and `done`, or `clarify`, `deny` or a final `error` with the last SQL; every event carries the run's trace id and a comment frame keeps the stream open every 15 seconds. Pydantic models define the request, every event and the ChartSpec contract. Each user may ask `RATE_LIMIT_PER_MINUTE` questions per minute (10 by default) before getting 429. A client that disconnects stops the run at its next node, which is logged as `cancelled`, and its running query is stopped through the new `agent_query_stopper` ClickHouse user, which may only list and stop queries and needs `CLICKHOUSE_QUERY_STOPPER_PASSWORD` in `.env`.
- Verify Keycloak access tokens in the api: an RS256 token signed by a key of the realm's JWKS (cached, refreshed at most every 30 seconds for an unknown key id), issued by `KEYCLOAK_ISSUER` for the `finch-api` audience and not expired is accepted, anything else gets 401; the token's realm roles map to one active pack role, the one named by an optional `X-Active-Role` header or else the first in `policies.yaml` order, and a token without a pack role gets 403. `GET /me` returns the signed-in user, their pack and console roles and the active role, and the public `GET /pack` names the active pack and its roles.
